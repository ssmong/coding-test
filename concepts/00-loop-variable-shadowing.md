# 루프 변수 shadowing — 바깥 변수는 복구되지 않는다

## 언제 쓰나

`for r in range(n)` / `for c in range(n)` 이중 루프 안에서, 모아둔 좌표 리스트를 다시 `for r, c in tmp:`로 순회할 때.

## 핵심 오해

> "`for`는 매 반복마다 다시 바인딩하니까 덮어써도 괜찮다"

**안쪽 루프 변수에만 참이다.** 바깥 루프 변수는 안쪽 루프가 다 돌 때까지 아무도 다시 바인딩하지 않는다.

## 코드

```python
for r in range(n):
    for c in range(n):
        if visited[r][c]:
            continue
        tmp = bfs(r, c)          # 연결요소 좌표들

        for r, c in tmp:         # ← r은 바깥 루프 변수! 오염된다
            grid[r][c] = avg
        # tmp 마지막 원소가 (3,4)였다면 여기서 r=3, c=4
        # 다음 반복: c는 range가 1로 재바인딩 → 복구됨
        #            r은 3인 채 → (0,1) 대신 (3,1)을 검사!
```

고치기 — **언패킹 루프는 무조건 새 이름:**

```python
        for tr, tc in tmp:
            grid[tr][tc] = avg
```

## 함정

- **예제로는 절대 안 잡힌다.** 오염된 `r` 때문에 어떤 칸이 BFS 시작점으로 스캔되지 않아도, 그 칸이 다른 연결요소에서 도달되면 결과가 우연히 맞는다. BOJ 16234에서 예제 5개는 전부 통과하고, 랜덤 3000케이스 스트레스에서야 172개 불일치로 드러났다.
- **크래시가 아니라 조용한 오답이다.** `visited` 가드가 인덱스 범위를 넘지 않게 막아주므로 IndexError도 안 난다.
- 같은 실수의 다른 얼굴: 거리 변수 `d`를 `for d in range(4)`(방향 인덱스)로 덮어쓰기 (4485). 방향 인덱스는 `d`가 관용이니 **거리 쪽 이름을 바꾼다.**

## 처방

1. 언패킹 루프(`for a, b in 리스트:`)는 항상 그 스코프에 없는 새 이름.
2. 루프 변수 이름은 함수 안에서 유일하게. 접미사(`tr`, `tc`, `nr`, `nc`)로 역할 구분.
3. 격자 문제는 제출 전 **독립 레퍼런스 대조 스트레스**(랜덤 수천 케이스). 예제 통과는 증거가 아니다.
